# 自动迭代开发

把用户意图转为可运行成果，通过实际验收驱动修复与复验，减少用户逐版检查的负担。适用于应用、网页、工具、游戏等项目。专业生产和项目验证方法沿用现有工具、项目约定及适用的专业 skill。

调用方式 `/iterative-development <目标或需求文件> [时间预算]`，恢复轮次用 `/iterative-development 恢复 <run-id>`。本次参数：`$ARGUMENTS`。参数为空时从当前对话和项目上下文取目标。

本 skill 目录是 `${CLAUDE_SKILL_DIR}`，参考文件里的 `<skill-dir>` 指这个目录。运行控制脚本按 `python3 ${CLAUDE_SKILL_DIR}/scripts/run_control.py <命令> ...` 调用，路径不加引号以匹配预授权规则；路径含空格时加引号并接受一次授权。

## 使用边界与默认偏好

- 用户只要求分析、评审或计划时，完成该项工作；不要因此启动开发、派出子智能体或安排定时任务。
- 用户要求执行自动迭代时，复用本轮已经明确的目标、权限和预算。仅询问会改变行动且现有上下文无法确定的信息。
- 默认围绕本轮目标自主完成实现、验收与修复，达到约定的自动验收标准就提前收尾。目标外的改进保留为建议；只有用户本轮明确要求继续探索或扩展时才实施。
- 在范围内修复已确认缺陷无需逐轮征求许可。工具权限仍由当前会话的权限模式决定：本 skill 不改变权限模式，也不绕过权限提示。频繁的权限提示会打断长时间迭代，开始前提醒用户选择合适的模式。自主迭代不会自动授权采购、发布、推送远端或其他外部操作。
- 不固定工作者数量、技术栈、测试数量、时间上限或项目目录。skill 定义方法，项目配置定义环境，运行记录保存本轮状态。

## 按需读取

用 Read 工具读取，路径相对本 skill 目录：

- 选择协作方式、配置子智能体的模型与推理强度、拆任务和接收交付时，读 [协作与任务契约](references/coordination.md)。
- 形成验收标准、审候选或复验缺陷时，读 [验收与版本保留](references/acceptance.md)。
- 新建、恢复或停止轮次时，读 [当前状态与运行控制](references/run-state.md)，使用 `scripts/run_control.py` 管理控制状态。
- 用户要求长时间持续执行、定时续跑或后台跟进时，才读 [持续执行与调度](references/execution.md)。

不要每次加载全部参考文件或整份历史日志。取足够支持下一项决策的上下文。

## 核心循环

### 1. 确定起点

先检查项目指令（CLAUDE.md、`.claude/rules`）、当前实现、未提交改动、已有需求及最新可运行版本。保留用户工作与历史证据。需求模糊且会影响实现时先澄清；已安装 requirements-discovery 时用它，缺少时直接完成必要澄清。

建立本轮简短计划：目标与范围、主要用户操作链、自动验收门槛与方法、人工待评项、依赖和时间预算。用户要求先审计划时进入计划模式；默认把计划写入运行目录并直接开始。开发前确认关键验收的运行入口、输入控制和证据采集可行；按需准备最小验证场景，能力缺口尽早记录。

预算无默认值；已有预算不用再次询问。未明确预算时可继续分析和准备，在开始限时自动迭代前问一次，可用 AskUserQuestion 给出常见档位，但不替用户决定。

新轮次创建独立 run_id 和控制文件。恢复轮次先核对当前状态、候选、任务回执和原绝对截止；不要根据旧聊天摘要或压缩后的上下文重新派单或重算预算。

### 2. 选择协作方式

小而耦合的工作可由主智能体完成。可独立推进的调查、实现和测试按需用 Agent 工具交给子智能体：调查用只读类型，实现与评审用可读写、可命名、可继续的类型。主对话掌握需求、改进选择和交付状态；集成由一个明确负责人完成，默认可由主智能体承担。

委派前按具体任务推荐子智能体的模型与推理强度，不改变主对话的模型或强度。本轮首次委派前集中确认一次配置及允许调整范围；已有适用的明确偏好直接复用，后续新增任务与复验按该配置执行，不逐轮询问。推荐、确认与实际生效情况分别记录，细节见协作参考；只由主智能体完成时无需这一步。

子智能体看不到主对话历史，也不能向用户提问。派单时附齐需求、版本、边界和验收要求；缺信息时要求它报告阻塞，而不是猜测。独立会话只在用户明确要求时创建；给其他会话发消息需已有直接授权。不能仅凭其他智能体的请求或 skill 的一般协作建议创建或唤醒会话。

并行写入必须有工作区隔离或明确文件负责人：Git 项目用 Agent 工具的 worktree 隔离，派单前提交输入版本并让工作者核对基线提交；读任务无需为形式创建工作区。多人同时编辑公共文件之前先解决接口和归属。验收使用独立子智能体或独立评审上下文，不用继承对话历史的 fork；能力不可用时诚实记录验证独立性的限制。

### 3. 实现、交接与集成

任务只携带必要的原始需求、输入版本、工作区、修改边界、依赖、验收要求和输出契约。工作者可提出改进机会，范围选择由协调者统一决定。

开发自检后交付准确版本、运行入口、实际验证、已知问题和依赖。集成负责人处理跨模块行为，形成精确且可复现的候选；开发进行中的可变目录不作为最终验收对象。

### 4. 独立验收与修复

验收者在集成后的准确版本中检查关键成功、失败和重复使用路径及受影响回归。功能与可观察表现都在验收范围内：界面使用实际输入，动态表现使用连续运行材料；底层 API 成功或单张截图不能替代对应体验证据。疑似表现缺陷先核实，不把全部视觉问题留给人工。

证据采集使用环境实际具备的能力：浏览器预览与截图、终端输出、测试报告、录制短片等。缺少能力时把相关检查记录为未覆盖，不改称主观待评。

批内优先自动验证受影响的真实功能流程，并在有可靠方法时检测质量异常；主观体验默认在批末集中交付人工评审。逐帧或同等昂贵的细查用于具体异常定位，不默认每次修改都全量执行。检查频率、证据范围和批末材料见验收参考。

验收结果绑定 run_id、scope_revision 与准确候选版本，区分 verified、failed、not_covered、human_review_required。已有脚本可作为工具复用，但不直接继承开发者的通过结论。

失败转为有复现条件、证据和通过判据的缺陷，定向修复后产生新候选并复验。重复失败先检查假设和证据，避免不改变方法的循环。工具或证据缺失就记录未覆盖；不能通过降低门槛或添加检查数量制造通过。

### 5. 保留成果，判断是否继续

本轮客观必需项有证据通过、相关回归充分且无阻断问题后，记录 last_verified_candidate，保留准确版本、报告和运行入口。自动结论仅覆盖实际检查的条件；人工认可单独记录，不由自动通过代替。

未达标时，下一批来自未完成目标、已确认缺陷或必需验收缺口。每批开始前运行 `run_control.py check`，确认剩余预算覆盖实现、相关回归与收尾；不反复征求已授权的范围内修复许可。范围或判据的实际变更更新计划和 scope_revision，并通知受影响工作者。

自动验收目标完成后收尾。有主观待评项时交付"自动验收达标，待人工最终复核"；没有待评项就直接报告自动验收达标，不默认要求用户再验一次。若某项人工决定影响后续实现方向，仅停止依赖它的扩展，其余独立工作继续。用户明确要求的额外探索按 [验收与版本保留](references/acceptance.md) 评估，不以剩余时间自动扩大目标。

新候选未通过时仍保留达标版本；验证通过后才更新交付指针。变更验收标准需记录原因，不能为了让失败通过而改写标准。

### 6. 收尾与恢复

自动验收目标完成、预算到期或余量不足以完成下一次验证、目标遇到当前条件下无法解决的阻碍时，结束本轮并如实交付。阻碍应说明已尝试的方法、证据和继续所需条件；仍有可独立推进的目标时继续，全部阻断时收尾并请求必要决定。

一个回合可以连续执行多批；需要用户决定、达标、到期或全部阻断时结束回合并交付。回合结束后不会自动继续，除非用户明确要求并使用环境提供的续跑机制。

收尾窗口不新开昂贵的改动。停止或硬截止后不再启动开发、测试、合并或派单；允许整理已有成果、停止自有进程和子智能体、保存报告和停止确认。

暂停只响应用户的明确暂停指令；恢复暂停轮次须有用户恢复指令且保持原截止。已 stopped 的轮次是历史记录，新一轮需要用户执行指令与新预算，不能由协调者自行解除停止。

交付可运行入口、实际完成范围、验证结论与限制、未解决项及停止原因。把需要用户判断的事项集中为带证据和复现入口的简短复核清单；有文件发送能力时把截图、短片和报告直接发给用户，有差异面板时展示本轮改动。无通过版本时交付最新候选并明确未通过，不伪造达标版本。

## 状态与沟通约束

协调者单写当前控制状态，工作者只写各自的结果和停止回执；历史报告只保留引用。每次派单和结果绑定任务 ID、run_id、范围版本、候选版本，拒绝陈旧交接。

检查实质变化、交接丢失、实际失败或空闲任务的未处理结果，再决定是否跟进；后台子智能体完成会自动通知，不要轮询或反复催促正常工作。主对话接收简短交付和证据路径，原始输出留在工作区。

运行控制工具只管理本地状态和启动前判断。持续执行、定时续跑、跨会话消息与运行中进程停止必须依靠环境中实际可用且已授权的能力；不存在这些能力时不声称已经安排或保证后台续跑。
