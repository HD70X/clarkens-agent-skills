# 持续执行与调度（Antigravity）

只在用户要求持续执行、定时续跑或后台跟进时读取。先检查当前环境实际提供的能力，沿用已有授权与运行机制；不为了使用 skill 新建一套守护框架。

## 执行方式

- Antigravity 的一个回合可以连续执行多批开发与验收，且子智能体与后台命令完成时会自动通过 Reactive Wakeup 唤醒主对话。当前会话足够完成时直接推进，完成后交付。
- 用户明确使用 `/goal` 或 `/teamwork` 时，配合环境提供的生命周期保留用户目标和预算。
- 需要延时检查或周期性跟进时，使用内置 `schedule` 工具：
  - 单次定时唤醒：`schedule(DurationSeconds=<秒>, TimerCondition="any", Prompt=...)`，调用后结束当前回合等待通知，**严禁使用 shell `sleep` 命令代替定时器**。
  - 周期性检查：`schedule(CronExpression="...", Prompt=...)`（仅在需要周期轮询外部状态时使用，收尾时用 `manage_task(Action="kill", TaskId=...)` 取消）。
- 不支持或未安排自动续跑时，保存状态、成果和下一步，明确告诉用户如何恢复（例如提供恢复指令与 `<run-id>`）。skill 文件与控制文件本身不是调度器。

`schedule` 的 `Prompt` 应精简引用当前 skill、控制文件及项目计划，不复制本轮完整历史：说明每次唤醒先检查当前 `run_id`、状态和绝对截止，复用已确认的模型配置与调整范围；仅处理实质变化、丢失交接和明确失败；本轮自动验收达标就收尾，到期或目标全部阻断时如实交付；停止后不自动恢复。

人工最终复核项随候选和证据集中交付；自动验收达标后不因等待主观反馈维持定时唤醒。需要人工决定才能继续实现时，说明受影响范围，继续其他独立目标；没有可推进目标就收尾。

## 时间与后台进程

所有恢复和重试沿用本轮绝对 `deadline_utc`。`close_at_utc` 是收尾提醒，不是续期；具体收尾余量可以按任务成本配置。临近截止不启动无法完成验证的新批次。

开始修改、测试、合并或派单前运行 `run_control.py check`。通过 `run_command` 执行耗时命令时：
- 若命令在 `WaitMsBeforeAsync` 内未完成，会自动转入后台任务并在结束时通知主对话。
- 使用 `manage_task(Action="list" | "status" | "kill")` 查看或终止当前会话的后台任务，只结束本轮启动的进程。
- 不要在循环中用 `manage_task` 轮询后台任务。

`run_control.py check` 只做只读判断，不会杀进程、取消 `schedule` 定时器或保持机器唤醒。它报告的 `may_work` / `may_start_task` 需要调用者遵守，不能当成系统已强制停止的证据。

本地调度依赖机器、应用和会话可用。会话关闭、机器休眠、断网或任务失败时不能保证续跑；再次运行后先检查原预算和状态，再决定能否继续。

## 收尾

1. 保存已有成果和停止原因；仍允许工作时先登记候选与评审再 `stop`，已截止时仅整理已有记录，不补登记新候选。区分自动验收达标、预算结束和阻碍，保留人工待评及未覆盖项、达标版本和最新候选。
2. 用 `manage_task(Action="kill", TaskId=...)` 停止本轮启动且仍在运行的测试进程、后台命令及不再需要的 `schedule` 定时器。
3. 对仍在运行的子智能体，若需保留其工作区未合并内容先发消息要求安全退出并合并，否则用 `manage_subagents(Action="kill", ConversationIds=[...])` 终止并核对结果。
4. 整理现有报告和剩余项。截止后只允许这类收尾，不再开开发、测试或合并。

暂停来自用户明确要求；恢复暂停轮次保留原截止。已停止轮次若需要继续，由用户决定新一轮目标和预算，使用新 `run_id`，历史控制与样品保留。
