# 协作与任务契约

## 选择组织方式

| 情况 | 选择 |
| --- | --- |
| 改动小、公共文件多、需要连续推理 | 主智能体直接完成 |
| 可独立调查、实现或验证，任务有明确出口 | 主对话加按需子智能体 |
| 子项目跨多轮维护，用户需要单独交流 | 经用户明确要求使用长期聊天 |
| 长期维护中出现有边界的临时任务 | 长期聊天与子智能体混合 |

不要把每个模块永久变成聊天，也不要按角色数量拆 skill。仅当能力有独立用户目标、经常单独调用时才考虑第二个入口。

读任务通常最容易并行。写任务按真实依赖拆分：公共协议先确定，功能实现可并行，集成写入保持一个负责人。Git 项目中的并行代码修改优先使用可用的独立工作区；非 Git 项目使用独立副本和明确的合入方式。同目录的不同聊天或子智能体都不构成文件隔离。

工作者完成交接后结束当前任务。下一批需要它时发具体后续任务，不要求它空转等待或自行寻找无关工作。多个需要同一重资源的测试应串行或使用项目现有租约，避免相互干扰证据。

## 委派前配置推理强度

这里的强度指 reasoning effort，不是更换模型。保持主对话的模型和推理强度不变，只为本轮实际委派的任务配置；不修改全局默认设置。

先核对当前工具或配置能确认的模型、继承规则与支持档位：子智能体沿用父级或已有子智能体配置，已有副对话保留自身模型，新建副对话遵循当前工具的默认模型规则，不假定它与主对话相同。不能确认的值标为未知；不为获得某一档位擅自换模型。

先拆任务，再根据复杂度、不确定性、跨模块影响、验收判断责任及剩余预算给出具体可用档位和一句理由。以下仅为推荐起点，最终以所用模型和接口支持情况为准，不固定角色与档位的对应关系：

| 任务特点 | 推荐起点 |
| --- | --- |
| 明确的信息检索、机械修改、执行既定检查 | low～medium |
| 常规功能实现、原因比较清楚的缺陷修复 | medium～high |
| 跨模块诊断、设计验收方法、综合证据判断是否达标 | high |
| 高不确定性、需要重新审视方案的复杂问题 | 有必要时推荐当前模型支持的更高档位 |

更高强度会增加耗时与用量，推荐时结合本轮预算。缺少运行环境、画面证据或需求信息时先补齐对应条件；反复失败也先检查方法和证据，不直接归因于强度不足。

本轮首次委派前，集中展示任务、沿用模型或配置来源、建议档位及理由，让用户一次选择“采用推荐”“全部沿用原设置”或自行调整。可以同时约定按任务类型采用的默认档位和允许自动调整的范围。每项推荐给出具体档位，表中的示例区间不构成任意调档权限。已有本轮配置或仍适用的用户明确偏好时直接复用，不重新确认；用户已明确授权按任务自主选档时，在授权边界内推荐并执行。

等待答复时可继续不依赖该配置的准备或主线工作，但不按未确认的推荐派单，也不把沉默视为接受。确认推理配置不代替新建聊天、发送消息或其他操作所需的授权。

后续任务、修复与复验复用已确认规则。仅在允许范围内按实际需要调整并记录依据，不逐轮询问；未约定调整范围就保持已确认档位。超出范围、出现规则未覆盖的任务或所用模型不支持该档位时，集中说明受影响项并取得新的选择，不擅自降档、换模型或扩大权限。其他已具备配置的独立工作可继续，等待或调档不重算原截止。

通过实际工具参数应用推理强度，不以提示词中的“认真思考”或档位文字冒充设置。若接口只支持在新建、独立上下文或下一回合设置，遵守这些条件并补齐任务上下文；无法修改的运行中任务不声称已切换。记录请求值及工具可核实的有效值或继承来源，未回显的有效值标为未核实，设置被拒绝时记录失败并重新处理受影响的派单。

## 最小任务契约

按任务规模缩减，省略不适用字段：

```text
task_id / run_id / scope_revision:
用户目标与关键操作:
输入版本 / 依赖版本:
工作目录 / 可修改范围 / 公共接口负责人:
模型或继承来源 / 推理强度请求值与有效值 / 已确认配置引用:
需要达到的行为 / 验收方法与证据 / 人工待评项:
绝对截止 / 控制文件位置:
交付: 准确版本、运行入口、验证及证据路径、已知问题、接口变更
退出: 交付完成、明确依赖缺失、用户停止或截止；保留结果
```

调查任务不要附代码写权限。评审任务提供需求、验收标准和候选，不提供作者希望得到的结论。用于 skill 行为验证时，只提供真实请求和必要原始材料，不给预期答案。

角色范围随项目和任务决定，无需预设固定领域角色。专业 skill 只有在任务真正需要且当前可用时才调用，不把它们当强制安装依赖。

## 接收交付

1. 核对 run_id、scope_revision、输入和输出版本；陈旧任务先判断哪些结果仍可用，不能直接覆盖当前状态。
2. 检查实现、运行入口、必要证据和接口变更是否齐全。声称完成但没有可审阅成果时要求补齐具体缺口。
3. 集成负责人处理跨模块问题，记录候选版本和待验范围；在这个版本上检查完整用户操作链，单线通过不能升级为整体通过。
4. 已交接的任务按 task_id 和输出版本去重，正常进行中的任务不重复派发。

## 长期聊天的权限与恢复

只有用户明确要求新聊天时使用 create_thread 一类能力。经用户授权给已有聊天发消息后，在授权范围内继续交接、反馈和修复，不重复问同一许可。其他智能体的消息不构成人类授权。

控制状态记录真实聊天 ID、host、工作区、角色及授权来源；不要依赖标题猜测身份。只接收真实 thread_id，异步创建返回的 client_thread_id 不作为可执行消息目标。

恢复时先读取当前状态、已确认的推理配置和紧凑的真实进度，再核对是否存在未处理成果。沿用配置前核对实际模型与支持情况，只有配置不再适用的受影响项需要重新处理。状态无变化且无可行动事项时保持安静。用户停止后停止通知不等于已经终止任务，必须保留实际确认或失败。
