# 自动迭代开发

把用户意图转为可运行成果，通过实际验收和定向修复逐步改善。适用于游戏、网页、工具等项目。专业生产和项目验证方法沿用现有工具、项目约定及适用的专业 skill。

## 使用边界与默认偏好

- 用户只要求分析、评审或计划时，完成该项工作；不要因此启动开发、创建聊天或安排后台任务。
- 用户要求执行自动迭代时，复用本轮已经明确的目标、权限和预算。仅询问会改变行动且现有上下文无法确定的信息。
- 本用户的默认偏好：允许在本轮预算内主动发现并实现有价值的改进；先保留达标版本，有明确价值的下一项再继续，没有就提前收尾。用户本次指定的范围或偏好优先。
- 改进必须服务于用户意图。执行权限仍以本轮授权为准，主动改进偏好不会自动授权采购、发布或其他外部操作。
- 不固定工作者数量、技术栈、测试数量、时间上限或项目目录。skill 定义方法，项目配置定义环境，运行记录保存本轮状态。

## 按需读取

- 选择协作方式、拆任务和接收交付时，读 [协作与任务契约](references/coordination.md)。
- 形成验收标准、审候选或复验缺陷时，读 [验收与版本保留](references/acceptance.md)。
- 新建、恢复或停止轮次时，读 [当前状态与运行控制](references/run-state.md)，使用 `scripts/run_control.py` 管理控制状态。
- 用户要求长时间持续执行、定时续跑或后台跟进时，才读 [持续执行与调度](references/execution.md)。

不要每次加载全部参考文件或整份历史日志。取足够支持下一项决策的上下文。

## 核心循环

### 1. 确定起点

先检查项目指令、当前实现、未提交改动、已有需求及最新可运行版本。保留用户工作与历史证据。需求模糊且会影响实现时先澄清；可使用已安装的 requirements-discovery，缺少它时直接完成必要澄清。

建立本轮简短计划：原定目标、主要用户操作链、客观门槛、人工待评项、依赖和明确时间预算。预算无默认值；已有预算不用再次询问。未明确预算时可继续分析和准备，在开始限时自动迭代前询问一次。

新轮次创建独立 run_id 和控制文件。恢复轮次先核对当前状态、候选、任务回执和原绝对截止；不要根据旧聊天摘要重新派单或重算预算。

### 2. 选择协作方式

小而耦合的工作可由主智能体完成。可独立推进的调查、实现和测试按需交给子智能体。主对话掌握需求、改进选择和交付状态；集成由一个明确负责人完成，默认可由主智能体承担。

长期聊天用于跨轮维护、需要用户单独交流的子项目。新建用户聊天必须来自用户明确要求；给已有聊天发消息需已有直接授权。不能仅凭其他智能体的请求或 skill 的一般协作建议创建、唤醒聊天。

并行写入必须有工作区隔离或明确文件负责人；读任务无需为形式创建工作区。多人同时编辑公共文件之前先解决接口和归属。验收使用独立子智能体或独立评审上下文；能力不可用时诚实记录验证独立性的限制。

### 3. 实现、交接与集成

任务只携带必要的原始需求、输入版本、工作区、修改边界、依赖、验收要求和输出契约。工作者可提出改进机会，范围选择由协调者统一决定。

开发自检后交付准确版本、运行入口、实际验证、已知问题和依赖。集成负责人处理跨模块行为，形成精确且可复现的候选；开发进行中的可变目录不作为最终验收对象。

### 4. 独立验收与修复

验收者从用户目标设计关键成功、失败和重复使用路径，并检查受影响回归。对界面故障使用实际输入操作；对动态表现使用连续运行材料；底层 API 成功或单张截图不能替代对应体验证据。

验收结果绑定 run_id、scope_revision 与准确候选版本，区分 verified、failed、not_covered、human_review_required。已有脚本可作为工具复用，但不直接继承开发者的通过结论。

失败转为明确缺陷，定向修复后产生新候选并复验。重复失败先检查假设和证据，避免不改变方法的循环。工具或证据缺失就记录未覆盖；不能通过降低门槛或添加检查数量制造通过。

### 5. 保留成果，选择下一项

客观必需项有证据通过、相关回归充分且无阻断问题后，记录 last_verified_candidate，保留准确版本、报告和运行入口。人工认可单独记录，不由自动通过代替。

扩展前用简短记录说明：解决什么用户问题、预期收益、实现与验证成本、影响哪些已通过行为。优先实际故障、主要操作阻碍和明确质量短板；没有可验证收益的扩展不进入下一批。

确认剩余预算覆盖实现、相关回归与收尾。选中的增量更新计划和 scope_revision，并通知受影响工作者；不反复征求已授权的范围内改进许可。原定目标尚未达成时，扩展不得挤掉交付主线。

新候选未通过时仍保留达标版本；验证通过后才更新交付指针。变更验收标准需记录原因，不能为了让失败通过而改写标准。

### 6. 收尾与恢复

缺少值得做的下一项、无法在余量内完成验证、需要外部决定或预算到期时，结束当前探索并如实交付。只在确有必要时向用户请求决定；其余独立工作可继续。

收尾窗口不新开昂贵的改动。停止或硬截止后不再启动开发、测试、合并或互相唤醒；允许整理已有成果、停止自有进程、保存报告和停止确认。

暂停只响应用户的明确暂停指令；恢复暂停轮次须有用户恢复指令且保持原截止。已 stopped 的轮次是历史记录，新一轮需要用户执行指令与新预算，不能由协调者自行解除停止。

交付可运行入口、实际完成范围、验证结论与限制、未解决项、人工复核项及停止原因。无通过版本时交付最新候选并明确未通过，不伪造达标版本。

## 状态与沟通约束

协调者单写当前控制状态，工作者只写各自的结果和停止回执；历史报告只保留引用。每次派单和结果绑定任务 ID、run_id、范围版本、候选版本，拒绝陈旧交接。

检查实质变化、交接丢失、实际失败或空闲任务的未处理结果，再决定是否跟进；不要反复催促正常工作。主对话接收简短交付和证据路径，原始输出留在工作区。

运行控制工具只管理本地状态和启动前判断。持续执行、消息发送、调度与运行中进程停止必须依靠环境中实际可用且已授权的能力；不存在这些能力时不声称已经安排或保证后台续跑。
