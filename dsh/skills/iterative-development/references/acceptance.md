# 验收与版本保留

## 开发前确定验收办法

每条必需要求对应起始状态、实际操作、预期结果、验证方法与证据来源。覆盖主要成功路径、最可能发生的失败以及重复使用；按真实变更选择边界，不机械生成测试清单。保留改前基线，修复后可比较原问题与受影响行为。

先确认关键验证所需的入口、运行环境、输入控制、代表性数据和证据采集可用。缺少时优先在授权范围内补齐最小验证条件；仍不可行就标记具体覆盖缺口及其对目标的影响。不要等到开发完成才发现无法验收，也不要求为所有项目建立专门测试框架。

## 区分可检查表现与人工判断

同一需求可以同时包含以下层次，分别记录结论：

| 层次 | 判据与证据 |
| --- | --- |
| 功能与明确约束 | 从真实入口执行操作，核对输出、状态、失败恢复及重复使用；内部检查辅助解释行为 |
| 可观察表现 | 在实际运行结果中检查已约定或可复现的显示、布局、动态与反馈缺陷；疑似问题补证据后再判定 |
| 体验与偏好 | 依据用户参考和目标作初步审查、准备对比材料；审美满意度、操作感受等由用户最终复核 |

选择能证明要求的证据：界面问题用实际输入与画面；动态行为用连续运行材料；持久化用跨进程重新打开后的结果。测试数据与用户数据隔离。日志、结构数据和数值指标可辅助定位，但不能替代所声称的外观或体验证据。单张截图不能证明完整动态过程，资源生成成功不能证明其在正式应用中的表现。

不要把全部视觉问题转为人工待评，也不要将未确认的审美偏好作为客观缺陷反复修改。自动判断限定于实际观察的场景、输入、视角及采样范围；未观察部分不外推为全部通过。用户给定的参考和明确约束优先于评审者个人偏好。需要具体方法时读 [跨项目验收示例](acceptance-examples.md)，只取与项目有关的例子。

简单低影响改动采用合适的轻量验证，不为了格式写镜像实现的测试。保存、状态转换、重复操作、并发或失败恢复等行为值得验证实际不变量。

## 按成本与风险安排检查频率

一批是围绕同一目标、可一起验证和比较的一组改动，不等于每次保存或每个提交。开发前选择能覆盖本轮风险的检查节奏，复用可靠方法；不为满足下表专门搭建昂贵框架。

| 检查对象 | 默认时机与方法 |
| --- | --- |
| 功能与机制 | 每个有意义的改动后自动检查受影响的真实流程；批末对集成候选完成关键操作链及必要回归 |
| 可测量的质量异常 | 有可靠检测方法时随相关改动检查并标记异常；阈值、基线和适用条件由项目确定 |
| 主观体验与价值 | 每批结束后准备代表性材料，供用户集中观看、操作或比较；不逐版打断用户，也不默认等待评价才继续独立目标 |
| 深入诊断 | 检查失败、异常标记或具体反馈出现时，针对相关片段逐帧查看、追踪日志或分析数据；修复后复验原问题 |

自动检查须经真实入口及相关控制器、事件和状态转换。可以通过自动输入驱动；仅在不绕过待测机制时采用无头运行。直接播放资源、调用底层函数或修改状态不能证明完整流程生效；界面缺陷仍须从实际界面复现。

异常检测只证明所测指标，不能推断整体体验优秀。核对异常是否超出项目约束或基线、是否可复现，再登记缺陷；不要仅凭一个代理指标反复重做。已确认的显示或动态故障进入修复，不全部推给最终人工评审。

涉及画面或体验变化时，批末保留准确候选在真实渲染环境中的代表性材料；批内机制检查不要求每次都完整录制和逐帧审查。日志或无头结果只用于其能证明的机制与指标，缺少必需画面证据时仍标记相关检查未覆盖。更高风险或明确的项目要求可提高检查频率，不为降低成本省略必需门槛。

## 候选与独立评审

验收绑定明确的 run_id、scope_revision、candidate_id 和准确版本。Git 提交或文件清单摘要均可作为版本身份；未跟踪但必须运行的资源也应纳入清单。冻结后不改候选，运行产生的缓存和数据放独立运行副本或目录。各任务交付后对集成版本执行完整操作链，不能把模块自检报告拼成整体通过。

评审者从原始需求设计关键路径，在适当隔离的环境中执行。可以复用开发的驾驶脚本，但应检查方法、夹具与断言是否真正覆盖需求，并补充最可能共享的盲区。独立环境和重新运行不自动保证判据独立。

结果逐项标记：

- verified：实际执行且证据支持；说明方法和适用版本。
- failed：实际与预期不符；提供缺陷标识、复现条件、步骤、实际、期望、严重性、证据和复验判据。
- not_covered：尚未执行、能力缺失或证据不足；不能算通过。
- human_review_required：需要用户决定的观感、手感或价值判断；说明具体待判断事项、可比较材料，以及该决定是否影响后续方向。能力缺失导致的必需检查未执行仍是 not_covered，不能改称主观待评以绕过。

下一轮根据未完成目标、确认缺陷和必需覆盖缺口选工作。修复后形成新候选，对照原问题复验并检查受影响回归。未变部分可在核对版本、环境和依赖后继承旧证据，注明范围和理由；不用重跑无关全库。范围或标准变化需更新 scope_revision，旧评审只能继承仍适用的部分。

重复失败时保留已尝试方法、失败证据和下一次尝试依据；没有新证据或可检验的新方法时，不通过反复重试耗尽预算。当前条件无法解决的阻碍需说明继续所需的输入或能力；独立目标仍可推进，目标全部阻断则收尾。

## 达标、保留与收尾

last_verified_candidate 必须有准确版本、实际运行入口和评审报告引用；客观必需项有证据通过、必要回归充分且无未解决阻断问题。存在 not_covered 的必需项时保留候选，不升级为达标版本。

自动验收达标后默认收尾。有主观待评项才标注“待人工最终复核”，没有则直接交付自动验收结论；不自动追加人工验收环节，也不把自动通过等同用户已经认可。主观待评不要求用户逐版检查，也不触发持续等待或自主重做。影响实现方向的人工决定只阻止依赖它的扩展，其余独立目标可继续。

仅在用户本轮明确要求额外探索时选择扩展：说明用户问题、改前基线、证据或假设、预期收益、实现与验证成本及受影响范围。验证收益与代价，不能仅以新功能通过推断整体更好。选中的改进才更新计划；原定目标优先，每批仍须来得及实现、复验与交付。其他机会记录为建议，不自动实施。

达标版本保持可运行。新候选通过后才更新交付指针，旧版保留用于比较和恢复；新候选失败不覆盖达标版本。涉及依赖、共享资源或数据结构变化时，同时保留旧版运行所需条件，采用适当隔离或恢复办法，避免只保留代码却无法运行。若从未达标，如实交付最新候选与缺陷。

## 完成记录

最终报告采用项目已有格式或最小清单：运行入口和版本、实际完成范围、自动验收结论与覆盖范围、证据及限制、未解决项和停止原因。到期或阻碍导致的结束不能称为达标；有价值的已完成部分仍应交付。

人工复核集中给出少量明确事项，每项附候选版本、代表性材料和实际复现入口；按需提供短视频、截图、前后对比或示例输出，说明希望用户判断什么。没有主观待评项时不用凑清单。原始日志留在证据目录，主对话提供可直接访问的必要证据，避免让用户重查所有历史版本。

每批交付可运行候选、检查结果与未覆盖项；涉及体验改进时默认附同条件前后对比，动态表现优先使用短片。尽量固定输入、场景、镜头、数据或随机种子，标明比较版本及无法保持一致的条件。人工反馈进入下一批已授权的工作；已停止或到期的轮次仍按运行控制规则处理，不因收到评价自动续跑。
