# 验收与版本保留

## 从用户任务推导证据

每条必需要求对应起始状态、实际操作、预期结果与验证方法。覆盖主要成功路径、最可能发生的失败以及重复使用；按真实变更选择边界，不机械生成测试清单。

| 领域 | 有效证据示例 |
| --- | --- |
| 界面交互 | 实际输入完成操作，观察结果，再执行下一步；拒绝或取消后仍可继续 |
| 游戏或动态画面 | 正式运行中的连续操作、相关镜头和环境；帧或骨骼指标仅辅助 |
| 命令行工具 | 真实进程、代表性合法和非法输入、退出码、输出、再次运行 |
| 持久化 | 保存后换进程重新打开，核对关键身份和数据；测试数据与用户数据隔离 |
| 跨模块功能 | 对集成后的准确候选完成完整操作链，不能只拼接模块自检报告 |

用户报告界面故障时，底层模型命令成功不能证明界面已修复。画面生成成功不能证明正式应用中的表现。数量、哈希或文档只能支持各自证明的事项，不能代替用户操作验收。

简单低影响改动采用合适的轻量验证，不为了格式写镜像实现的测试。保存、状态转换、重复操作、并发或失败恢复等行为值得验证实际不变量。

## 候选与独立评审

验收绑定明确的 run_id、scope_revision、candidate_id 和准确版本。Git 提交或文件清单摘要均可作为版本身份；未跟踪但必须运行的资源也应纳入清单。冻结后不改候选，运行产生的缓存和数据放独立运行副本或目录。

评审者从原始需求设计关键路径，在适当隔离的环境中执行。可以复用开发的驾驶脚本，但应检查方法、夹具与断言是否真正覆盖需求，并补充最可能共享的盲区。独立环境和重新运行不自动保证判据独立。

结果逐项标记：

- verified：实际执行且证据支持；说明方法和适用版本。
- failed：实际与预期不符；提供复现条件、步骤、实际、期望、严重性和证据。
- not_covered：尚未执行、能力缺失或证据不足；不能算通过。
- human_review_required：需要用户决定的观感、手感或价值判断；说明可比较材料。

修复后形成新候选，复验缺陷与受影响回归。未变部分可在核对版本、环境和依赖后继承旧证据，注明范围和理由；不用重跑无关全库。扩展或标准变化需更新 scope_revision，旧评审只能继承仍适用的部分。

## 达标与探索

last_verified_candidate 必须有准确版本、实际运行入口和评审报告引用；客观必需项有证据通过、必要回归充分且无未解决阻断问题。存在 not_covered 的必需项时保留候选，不升级为达标版本。

人工认可与客观通过分别标注。若存在已确认视觉故障，它应作为可复现缺陷；不要把所有表现问题都移到人工待评。主观满意度无法自动决定时保留待复核，不能因此无限循环。

探索前写一条机会记录：用户问题、证据或假设、预期收益、实现与验证成本、受影响范围。选中的改进才更新本轮计划，工作者不各自扩范围。先完成原定目标；后续每批仍应能在余量内实现、复验与交付。

达标版本保持可运行。新候选通过后才更新交付指针，旧版保留用于比较和恢复；新候选失败不覆盖达标版本。若从未达标，如实交付最新候选与缺陷。

## 完成记录

最终报告采用项目已有格式或最小清单：运行入口和版本、实际完成范围、客观结论、证据及限制、未解决项、人工复核项、停止原因。原始日志留在证据目录，主对话只接收必要摘要。
